# GlassGamePanel

GlassGamePanel is the GlassHosting / Glasshouse control plane for game-server operators: OpenAPI-first API, Wings executor path, and a **free** DIY Wings one-click installer for an operator-owned node.

## Free Wings installer

One-click packaging for **your** machine and **your** panel — branded GlassGamePanel / GlassHosting. It does **not** grant GlassHosting hosting capacity.

## Product snapshot

- **OpenAPI stub:** `0.1.5-stub` (draft API surface; no public production panel-api endpoint yet)
- **Executor:** Wings (Ptero-shaped) behind this API; Proxmox driver later
- **Managed inventory:** GlassHosting-managed servers you do not own are refused by default (deny map in-repo)
- **Test runtime:** `cmd/panel-api-test` — local/test control plane; Wings dials only when explicitly allowlisted
- **Glass Watch:** standalone product; SSO via Portal when linked — not this monolith
- **Identity:** same-email unique across Portal / panel / Watch (merge on match)

## Test runtime

Minimal Go control plane for the test gate. The default executor is noop and does not dial Wings, Pterodactyl, WHMCS, or Stripe. `PANEL_WINGS_EXECUTOR=real` dials the Wings daemon only when `PANEL_WINGS_ALLOWLIST` names the target and both `PANEL_WINGS_BASE_URL` and `PANEL_WINGS_TOKEN` are set. An empty allowlist, a missing daemon origin, and the noop executor perform zero dials. File content writes dial only for an allowlisted UUID under `mods/` or `plugins/` (`.jar` / `.zip`). GlassHosting-managed inventory stays refused. Do not set `real` on the test container or production in a casual change — that flip is a separate, gated apply. See [`docs/phase-c-wings-allowlist.md`](docs/phase-c-wings-allowlist.md) and [`docs/phase-d2-files-write.md`](docs/phase-d2-files-write.md).

| Path | What |
|------|------|
| [`cmd/panel-api-test`](cmd/panel-api-test) | Process entrypoint. `GET /healthz` → `{"ok":true}` |
| [`internal/`](internal) | Deny middleware, test JWT, tickets, rate limit, migration fixture |
| [`managed-inventory-deny.json`](managed-inventory-deny.json) | Managed-inventory deny map (must match `internal/deny/managed-inventory-deny.json`) |

```bash
go test ./...
go build -o dist/panel-api-test ./cmd/panel-api-test
```

Default listen is **`127.0.0.1:8080`**. The process refuses any other bind except explicit `0.0.0.0:8080` or `[::1]:8080`. There is no public listen default and no OpenAPI/Swagger UI.

**Portal OIDC RS256** is the only staff verifier (Gate 2b Option A). The default JWKS URL is `https://portal-test.glasshosting.internal/oidc/jwks.json`. Staff JWTs must be RS256, `kid`-selected from that JWKS (a new kid is fetched without a restart; a sole key may omit `kid`). Issuer and audience stay test-bound. Wrong `aud`, `iss`, or `alg` is 401. An HS256 staff token is 401 even when `PANEL_JWT_HMAC_SECRET` is set. A `/.well-known/` JWKS URL is rejected at startup because portal-test nginx returns 403 for that prefix. This process does not mint Portal tokens and does not discover OIDC metadata; it GETs the configured JWKS URL only. A Portal-minted agent RS256 token is accepted on the same JWKS path.

**Agent HMAC (`PANEL_JWT_HMAC_SECRET`)** stays required so `POST /v1/agent-tokens` can mint HS256 agent JWTs. Those tokens still authenticate under the same test iss/aud. The secret is not a staff accept path. Prod aud/iss is rejected on the staff RS256 path and on the agent HS256 path.

The Portal JWKS GET is the staff verifier's outbound client. It does not dial Wings. When `PTERO_SOURCE_API_URL` and `PTERO_SOURCE_API_TOKEN` are both set, migration discovery does one read-only Application API GET for servers and allocations. That client does not follow redirects, does not use the request body token, and does not dispatch Wings. Unset, `inventory_only` stays on the in-process fixture and does not dial. The Wings daemon client in `internal/wings` is a separate outbound path. It POSTs power and GETs a directory listing only for an allowlisted, non–managed-inventory target when the executor is `real` and the daemon origin and token are both set. It does not follow redirects. The token is not logged. Console tickets do not use it. Managed inventory stays refused. Agent mint, console tickets, and migration `inventory_only` / `dry_run` are served under `/v1`. Mutating routes require `Idempotency-Key`. Confirm is refused while the mode ceiling is `inventory_only` or `dry_run`. Rollback is a 72h design stub and does not mutate.

`GET /v1/servers` requires `servers:read` and returns an in-memory page. The commercial fixture `11111111-1111-4111-8111-111111111111` is seeded with planned Glass id `bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb` and `wings_server_id` null. Managed-inventory deny UUIDs are not listed and are not Wings targets. `GET /v1/servers/{serverId}` uses the managed-inventory deny middleware and agent `server_ids` binding, so a deny UUID is 403 (managed-inventory refuse).

`POST /v1/servers` still returns **202** `server.create`, and the in-process worker completes that job before the response is written. The worker claims the next free IPv4+IPv6 pair from `tor-n5-ula-test` (node **5**, ULA pool ports **25600–25631**). Each allocation row includes `family`. The Glass UUID is new; `wings_server_id` stays null. With the default executor, `X-Glass-Executor` is `noop` and `X-Glass-Wings-Dispatch` is `0`. Create does not dial Wings. The same `Idempotency-Key` replays the original job and does not claim a second pair. GlassHosting-managed servers the caller does not own are refused with **403** before a claim. See [`docs/phase-a-create-dualstack.md`](docs/phase-a-create-dualstack.md) and [`docs/phase-c-wings-allowlist.md`](docs/phase-c-wings-allowlist.md).

### Test container cutover

Target container: `lxc-gh-glassgamepanel-test-01`. Upstream for `https://panel-api-test.glasshosting.internal` is the test CT underlay `:8080`. WireGuard allowlists stay at the gateway; this binary does not configure DNS or WireGuard.

1. Build `panel-api-test` from this commit and install it on the test container (for example `/usr/local/bin/panel-api-test`).
2. Install [`deploy/panel-api-test.service`](deploy/panel-api-test.service). It sets `LISTEN_ADDR=0.0.0.0:8080` so the underlay address accepts the existing gateway proxy.
3. Copy [`deploy/panel-api-test.env.example`](deploy/panel-api-test.env.example) to `/etc/glass/panel-api-test.env`. Keep `PANEL_JWT_JWKS_URL` at `https://portal-test.glasshosting.internal/oidc/jwks.json` and replace `PANEL_JWT_HMAC_SECRET`. Do not use `/.well-known/` (nginx 403). Do not point JWKS at prod Portal and do not reuse a prod signing key. The HMAC secret signs panel-minted agent tokens. It does not authenticate staff.
4. Stop the `/healthz` stub on `:8080` and start `panel-api-test`. Both `/healthz` and `/v1/healthz` return `{"ok":true}` with `X-Glass-Runtime: panel-api-test`.
5. From the WireGuard side, curl the container underlay `/healthz` and expect that header and `X-Glass-Wings-Dispatch: 0`.
6. Do not add public DNS. Leave `PANEL_WINGS_EXECUTOR` unset (`noop`) and leave `PANEL_WINGS_BASE_URL` and `PANEL_WINGS_TOKEN` empty until a separate gated apply. GlassHosting-managed servers you do not own stay refused (see the deny map).

Gateway rate limits (60 mutate / 300 read rpm) are already live and are **ops-attested**. The process enforces the same caps per token `jti` and will not boot with a higher cap. See [`artifacts/api-evidence/rate-limit-60-300.json`](artifacts/api-evidence/rate-limit-60-300.json).
